Chapter 22Part V · Building a localization

A template for any localization, and how to review one

The few pieces every country module needs, why each one exists, how it stays correct year after year, and a checklist to review it

After this chapter you can
  • Say what a payroll localization is and name its five groups of pieces
  • Write the data of a country module (structure, categories, rules, dated parameters) and explain why each field is written that way
  • Add the Python a country needs (wiring hooks, version fields, guarded overrides) and only that
  • Produce the outputs (declarations, accounting) and prove the module with golden-payslip tests
  • Run the yearly upkeep, and review a localization with a graded checklist

A company in a new country wants Odoo Payroll. The engine is ready: Part IV showed that it runs any rules it is given. What is missing is the country: its rules, its rates, its forms. This chapter is the template for that country module, piece by piece. For each piece it says why it exists (what breaks without it), what the code does, and when you need it. It ends with a review checklist, because a payroll bug never crashes: it pays someone a little wrong every month until the year-end reconciliation finds it.

Every snippet uses the country code xx and follows a real module: the Dutch one (l10n_nl_hr_payroll, almost only data), the Mexican one (l10n_mx_hr_payroll, several engine hooks) and the Belgian one (l10n_be_hr_payroll, the largest).

22.1 What a localization module is

A payroll localization (also country module, l10n module) is the country layer of Chapter 9: one or two Odoo modules, l10n_xx_hr_payroll and l10n_xx_hr_payroll_account, that turn one country's payroll law into records and a little Python on top of the shared engine. The engine, payslips, pay runs, work entries and the declaration framework stay in hr_payroll; the localization brings only what the country knows.

Three things follow:

  • It is mostly data. Rules, categories and dated parameters (Part IV) carry the law. Python is for what data cannot say, and stays small.
  • It must stay correct every year. The law changes every January, sometimes more often; the module is built so that a change is a new record that reaches every customer within a week.
  • It must be provable. Nobody can check forty rules by reading them; golden payslips frozen as tests do.

22.2 The skeleton: two modules and a manifest

A localization is two modules, not one, because payroll and accounting are separate purchases. Some customers run payroll in Odoo and send the totals to an outside accountant; and the accounts a rule posts to belong to the country's chart of accounts (l10n_xx), which the payroll module must not force on anyone.

l10n_xx_hr_payroll
The law. Depends only on hr_payroll and hr_holidays, so it installs in any database with payroll.
data/categories, structure type, structures, dated parameters, rules, time-type settings
models/the wiring hooks, fields on the version, declarations, overrides
views/the payslip PDF, version fields on the employee form, declaration screens
security/access rights for any model the module adds
l10n_xx_hr_payroll_account
The bridge. Depends on hr_payroll_account, the chart l10n_xx and the module on the left; installs itself when both sides are present.
models/which account each rule posts to
data/loads that mapping for existing companies; marks the net as the employee's debt
tests/the golden payslips: the test base needs a company with a chart
otherany e-filing that needs accounting (Mexico's electronic payslip)

The name is not cosmetic. Reset on a rule or a parameter reloads only the modules whose name starts with l10n_<country code>, and the structure's payslip-report field offers only reports whose name contains it. A module called xx_payroll installs fine, but Reset never restores its rules.

The manifest of the main module, following the Dutch one:

{
    'name': 'Xxland - Payroll',
    'countries': ['xx'],
    'category': 'Human Resources/Payroll',
    'depends': ['hr_payroll', 'hr_holidays'],                 # ①
    'auto_install': ['hr_payroll'],                           # ②
    'data': [                                                 # ③
        'data/hr_salary_rule_category_data.xml',
        'data/hr_payroll_structure_type_data.xml',
        'data/hr_work_entry_type_data.xml',
        'views/hr_payroll_report.xml',
        'data/hr_payroll_structure_data.xml',
        'data/hr_rule_parameters_data.xml',
        'data/hr_salary_rule_data.xml',
        'views/report_payslip_templates.xml',
        'views/hr_employee_views.xml',
    ],
    'demo': ['data/l10n_xx_hr_payroll_demo.xml'],
    'post_init_hook': '_l10n_xx_hr_payroll_post_install',    # ④
    'author': 'Odoo S.A.',
    'license': 'OEEL-1',
}
1
No accounting, no chart. hr_holidays is there because time off produces the work entries the payslip pays. Add a dependency here only if a rule or a model really needs it.
2
Installs itself. With countries, Odoo installs it with payroll only when a company of country xx exists. Without it, a customer must know the module exists.
3
Load order. Odoo loads files top to bottom, and a reference to a record not yet loaded fails the install. So: categories before the rules that use them, the structure type before the structure, the report action (hr_payroll_report.xml) before the structure that names it, the structure before its rules.
4
Post-install hook. Switches existing data to the country's time types (§22.5).
When
Always. The account module's manifest is the same shape: depends on the three modules above, auto_install on the main module and hr_payroll_account.

22.3 The pay structure and the categories

The first data file gives the payslips a home: a structure type for the employees' versions, and a structure listing the rules. These are the Dutch records, renamed:

<record id="structure_type_employee_xx" model="hr.payroll.structure.type">   <!-- ① -->
    <field name="name">Xxland: Employee</field>
    <field name="country_id" ref="base.xx"/>
</record>

<record id="hr_payroll_structure_xx_employee_salary" model="hr.payroll.structure">  <!-- ② -->
    <field name="name">Xxland: Regular Pay</field>
    <field name="code">XXMONTHLY</field>
    <field name="country_id" ref="base.xx"/>
    <field name="type_id" ref="structure_type_employee_xx"/>
    <field name="report_id" ref="action_report_payslip_xx"/>
    <field name="rule_ids" eval="[]"/>                                       <!-- ③ -->
</record>
<record id="structure_type_employee_xx" model="hr.payroll.structure.type">   <!-- ④ -->
    <field name="default_struct_id" ref="hr_payroll_structure_xx_employee_salary"/>
    <field name="default_work_entry_type_id" ref="hr_work_entry.xx_work_entry_type_attendance"/>
</record>
1
The structure type is what HR picks on each employee's version (Chapter 19). Its country hides it from companies of other countries.
2
The structure is the list of rules for the regular payslip, with the country's payslip PDF.
3
rule_ids eval="[]": a new structure otherwise receives a copy of the framework's generic rules (basic, gross, net), which would then sit next to the country's own and duplicate their lines.
4
A second write on the type. The type must name its default structure, and the structure needs its type: neither can be created first with both links. So the type is created bare, then completed. It also names the time type used for normal work (Chapter 14).
When
Always. Add one structure per kind of payslip the law taxes or declares differently (a 13th month, a termination); a bonus paid without worked days sets use_worked_day_lines to False.

Then the categories, the running totals of Chapter 20. Design them from the declarations: each total a form asks for, and each base the law computes something on, gets a category.

<record id="hr_salary_rule_category_social_security_employee" model="hr.salary.rule.category">
    <field name="name">Employee Social Security Deductions</field>
    <field name="code">SOCIALSECURITYEMPLOYEE</field>
    <field name="parent_id" ref="hr_payroll.DED"/>                           <!-- ① -->
    <field name="country_id" ref="base.xx"/>
</record>
1
Parent DED. Everything added here also rolls up into the deductions, so the generic net formula sees it unchanged (Chapter 20). The declaration reads the child category for its "employee social security" box.
When
One per legal base or declaration box. Most countries keep the generic chain and add children (Netherlands, Mexico); a country where many items enter and leave the net at different points uses a running net instead (Belgium, Chapter 20).

Last, the time types. They are created for each country in the community module hr_work_entry, so attendance and time off work without payroll. The payroll module only says which total each one feeds:

<record id="hr_work_entry.xx_work_entry_type_attendance" model="hr.work.entry.type">
    <field name="category_ids" eval="[(6, 0, [ref('hr_payroll.BASIC')])]"/>
</record>

Without this line, the worked-days amount is on the payslip but never reaches BASIC, so the gross and the net miss it (the pitfall of Chapter 20). Write one such record for every paid time type of the country.

22.4 Rules

A rule is a record with five parts (Chapter 19). In a localization it is written in XML, and how it is written decides whether Odoo can keep it correct later. Here is the Dutch old-age contribution, simplified and renamed:

<record id="l10n_xx_old_age_insurance" model="hr.salary.rule">
    <field name="name">Old Age Insurance</field>
    <field name="code">XX_OLD_AGE</field>                                    <!-- ① -->
    <field name="sequence">105</field>                                       <!-- ② -->
    <!-- ③ -->
    <field name="category_ids" eval="[(6, 0, [ref('hr_salary_rule_category_social_security_employee')])]"/>
    <field name="condition_select">none</field>
    <field name="amount_select">code</field>
    <field name="amount_python_compute">                                     <!-- ④ -->
rates = payslip._rule_parameter('l10n_xx_social_security_rates_employee')['OLD_AGE']
result_rate = -rates[0]
result = min(categories['GROSS'], rates[1] / 12)
    </field>
    <!-- ⑤ -->
    <field name="struct_ids" eval="[(6, 0, [ref('hr_payroll_structure_xx_employee_salary')])]"/>
    <field name="country_id" ref="base.xx"/>
</record>
1
The code is how later rules (result_rules['XX_OLD_AGE']), tests and declarations find this line. Choose it once; renaming it breaks all three.
2
Sequence 105: after GROSS (100), which the formula reads; a rule placed before it would read 0 without any error (Chapter 19). Leave gaps: next year's new contribution fits in at 107 without renumbering.
3
(6, 0, [...]) means "exactly this list". The weekly update rewrites only what the XML says. Written as "add this category" ((4, id)), a category you later remove from the XML would stay in every customer database. Same reason to write the condition, the amount, the structures and the country every time, even when they look like defaults.
4
The formula. Line 1 reads the rate and the yearly cap from a dated parameter (§22.5). Line 2 sets the rate, negative because a deduction lowers the net. Line 3 sets the amount: the taxable salary, capped at a twelfth of the yearly cap. The payslip line then shows base × rate, which anyone can check. No number is written in the code: a literal can only change with a code release, and since rules are not dated, changing it also changes every old payslip you recompute (Chapter 21).
5
Structures. The rule runs only on these. A contribution due on the 13th month too must list that structure as well.
When
One record per line the law defines on a payslip.

Three habits keep rules reviewable:

  • A long formula goes to a helper. Past about ten lines, move the computation to a method on hr.payslip and call it from the rule (result = payslip._get_xx_income_tax()); a method can be tested alone and read with an editor.
  • Never rely on leftovers. All rules of a payslip share one dictionary, so a variable set in one rule is still there in the next. Read earlier results through result_rules or categories instead, and never name a variable like a helper (date).
  • Every total a rule reads is fed by an earlier rule. A misspelt or empty category reads 0, silently.

22.5 Dated parameters and the three wiring hooks

The rule above asked for l10n_xx_social_security_rates_employee. Here it is, in the Dutch shape (the values are placeholders):

<record id="rule_parameter_social_security_rates_employee" model="hr.rule.parameter">
    <field name="name">Xxland: Employee Social Security Rates and Thresholds</field>
    <field name="code">l10n_xx_social_security_rates_employee</field>     <!-- ① -->
    <field name="country_id" ref="base.xx"/>
</record>
<!-- {code: [rate, yearly cap]} -->                                       <!-- ② -->
<record id="rule_parameter_social_security_rates_employee_2025" model="hr.rule.parameter.value">
    <field name="parameter_value">{
    'OLD_AGE': [17.9, 35129.00],
    'SURVIVOR': [0.1, 35129.00],
}</field>
    <field name="rule_parameter_id" ref="rule_parameter_social_security_rates_employee"/>
    <field name="date_from" eval="datetime(2025, 1, 1).date()"/>          <!-- ③ -->
</record>
1
The parameter is only a name and a code; rules ask for the code. Prefix it with l10n_xx_: one database holds every installed country's parameters, and two countries would otherwise collide on social_security_rates.
2
The shape (here, a rate and a cap per contribution) is chosen once and kept every year, so the rule never needs to know the year. The comment documents it for the next developer.
3
The value's start date is the date the law takes effect. It lasts until the next value; the record's id ends with the year, so next year is a new record (§22.10).
When
For every number, scale or table the law sets. How a payslip picks its value is in Chapter 21.

Records are not enough on their own. Three small hooks connect them to the rest of Odoo; every localization has all three.

Hook 1: the update list. It tells the weekly job which files to reload:

class HrPayslip(models.Model):
    _inherit = 'hr.payslip'

    def _get_data_files_to_update(self):                               # ①
        # Note: file order should be maintained
        return super()._get_data_files_to_update() + [(
            'l10n_xx_hr_payroll', [                                     # ②
                'data/hr_salary_rule_category_data.xml',
                'data/hr_payroll_structure_type_data.xml',
                'data/hr_payroll_structure_data.xml',
                'data/hr_rule_parameters_data.xml',
                'data/hr_salary_rule_data.xml',
            ])]


class HrWorkEntryType(models.Model):
    _inherit = 'hr.work.entry.type'

    def _get_data_files_to_update(self):                               # ③
        return super()._get_data_files_to_update() + [(
            'l10n_xx_hr_payroll', ['data/hr_work_entry_type_data.xml'])]
1
Why. The scheduled action Payroll: Update data reloads, every week and in every database, exactly the files listed here. A file not in the list is loaded at installation and never again: a fixed rate in it reaches new customers only.
2
Same order as the manifest, for the same reason: a file can only refer to records loaded before it.
3
Time types have their own list, reloaded in a separate step, after the community time types are created, so the references in the file always resolve.

Hook 2: the post-install hook, in the module's __init__.py:

def _l10n_xx_hr_payroll_post_install(env):
    env.ref('base.xx')._adapt_work_entry_types_to_country()

A database that already used Odoo before installing payroll has schedules, time off, allocations and structure types pointing at the generic time types. This call switches those of the country's companies to the country's own time types with the same code. Without it, existing employees keep generic types that carry none of the country's payroll settings.

Hook 3: the pay frequencies the law allows:

class HrPayrollStructureType(models.Model):
    _inherit = 'hr.payroll.structure.type'

    def _get_selection_schedule_pay(self):
        if self.env.company.country_code == 'XX':
            return [('monthly', self.env._('month'))]
        return super()._get_selection_schedule_pay()

The structure type's Scheduled Pay field offers only these choices, so nobody runs a weekly payroll where the law and the rules only know months. The test is on the current company's country; other countries fall through to super(). Mexico lists seven frequencies, including 10 and 14 days, and also overrides _schedule_timedelta on hr.payslip to tell the engine where such a period ends.

22.6 Payroll warnings

A payslip computed from incomplete data is wrong without any error: an employee with no sector gets no sector rules, an employee with no bank account cannot be paid, a missing national number gets the declaration rejected months later. A payroll warning catches that earlier. It is a data record (hr.payroll.warning) holding a check, either a domain or a few lines of Python. Every record that matches it appears on a card of the payroll dashboard, with a button to open the list; a warning can also block the validation of those employees' payslips.

The framework ships the generic ones (Missing Bank Account); a localization adds the checks its law needs. Belgium's meal-voucher check:

<record id="hr_payroll_warning_incorrect_configuration_meal_voucher" model="hr.payroll.warning">
    <field name="name">Incorrect Meal Voucher Configuration</field>                 <!-- ① -->
    <field name="description">Its value cannot exceed €10 and must be greater than the employee's share, which cannot be less than €1.09.</field>
    <field name="country_id" ref="base.be"/>                                         <!-- ② -->
    <field name="warning_color_class">warning</field>
    <field name="button_name">Review Employees</field>
    <field name="block_payslips">True</field>                                        <!-- ③ -->
    <field name="warning_type">domain</field>                                        <!-- ④ -->
    <field name="model_id" ref="hr.model_hr_employee"/>
    <field name="warning_domain">[('is_meal_voucher_valid', '=', False)]</field>
</record>
1
Title and description, as shown on the dashboard card. Say what is wrong and what the law requires, so the payroll officer can fix it without asking.
2
Country. Only companies of this country see it. The generic warnings leave it empty.
3
Blocking. Validating a payslip of a matching employee fails with the warning's name. Without it, the card only informs.
4
The check: a domain on a model; every matching record is listed. When a domain cannot express it, use warning_type python and an evaluation_code that sets warning_records (Belgium's invalid national numbers).
When
One per piece of data the rules or the declarations cannot do without. Make it blocking only when every payslip of the employee would be wrong or unpayable, and the fix is quick (a voucher amount out of the legal range). Data that matters for a later filing (Belgium's Employees without a Joint Committee) stays a plain card: blocking it would stop the whole pay run for something that can be fixed before the declaration.

22.7 Python: fields on the version and guarded overrides

Python enters only when data cannot express the law. The two most common reasons are a fact about the person the standard version lacks, and an engine step that works differently in the country (the ladder of Chapter 21).

A fact about the person goes on the version. The Dutch 30 % ruling for skilled migrants, renamed:

class HrVersion(models.Model):
    _inherit = 'hr.version'

    l10n_xx_30_percent = fields.Boolean(                                  # ①
        string="30% Exemption", groups="hr_payroll.group_hr_payroll_user", tracking=1)

    @api.model
    def _get_whitelist_fields_from_template(self):                        # ②
        whitelisted_fields = super()._get_whitelist_fields_from_template() or []
        if self.env.company.country_id.code == "XX":
            whitelisted_fields += ["l10n_xx_30_percent"]
        return whitelisted_fields


class HrEmployee(models.Model):
    _inherit = 'hr.employee'

    l10n_xx_30_percent = fields.Boolean(                                  # ③
        readonly=False, related="version_id.l10n_xx_30_percent", inherited=True,
        groups="hr_payroll.group_hr_payroll_user")
1
On the version, not the employee, because the fact can change and versions are dated (Chapter 13): a payslip of last year reads last year's situation. groups hides it from users without payroll rights; tracking logs every change for audits.
2
Whitelist. Contract templates copy only whitelisted fields into new versions; the country test keeps other countries' templates unchanged.
3
Mirror on the employee, so HR edits it on the employee form like any standard version field. The view shows it only when country_code is the country's.
When
Only when a rule needs a fact the version lacks. If a rule reads the field, also add it to _get_fields_that_recompute_payslip, or draft payslips keep the old amount until someone clicks Compute. A list with its own life (Mexico's housing-loan deductions) becomes its own model, with access rights and a multi-company rule.

An engine override changes one step for one country. Mexico values a worked-days line from a legal daily salary instead of the monthly wage:

def _compute_amount(self):
    mx_worked_days = self.filtered(
        lambda wd: wd.payslip_id.struct_id.country_id.code == "MX")     # ①
    for worked_days in mx_worked_days:
        ...   # value the line from the Mexican daily salary            # ②
    return super(HrPayslipWorkedDays, self - mx_worked_days)._compute_amount()  # ③
1
The country guard. One database can hold a Mexican and a Belgian company. Keep only the records of your country, here through the payslip's structure.
2
Your country's logic, on those records only.
3
Everything else goes to super(): other countries get the standard behaviour, and other modules' overrides of the same method still run. Forget the guard and Belgian payslips are valued the Mexican way; forget super() and every other country's worked days stay at zero.

Which hook to override depends on what the law asks. These are the ones localizations use, all on hr.payslip unless noted:

22.8 Declarations and the accounting bridge

A module the customer cannot file with is not finished. Most countries require at least a yearly certificate per employee (what was paid and withheld). The framework gives a mixin with the year, one line per employee, background PDF generation and the screens; a localization fills in four methods. Following the Kenyan certificate:

class L10nXxAnnualCertificate(models.Model):
    _name = 'l10n_xx.annual.certificate'
    _inherit = ['hr.payroll.declaration.mixin']
    _description = 'Annual Salary Certificate'

    def _country_restriction(self):                                       # ①
        return 'XX'

    def action_generate_declarations(self):                               # ②
        for sheet in self:
            payslips = self.env['hr.payslip'].search([...])  # validated, this year
            sheet.line_ids = [(5, 0, 0)] + [(0, 0, {
                'employee_id': employee.id, 'res_model': self._name, 'res_id': sheet.id,
            }) for employee in payslips.employee_id]
        return super().action_generate_declarations()

    def _get_rendering_data(self, employees):                             # ③
        ...   # {employee: {...}} from payslips._get_line_values(['GROSS', 'XX_TAX'])

    def _get_pdf_report(self):                                            # ④
        return self.env.ref('l10n_xx_hr_payroll.action_report_annual_certificate')
1
Only companies of the country can open the screen.
2
Who gets a certificate: one line per employee with a validated payslip in the year. The mixin's super() refuses an empty declaration.
3
The numbers, read from payslip lines by code or category, never recomputed. If the certificate is wrong, the payslips are (Chapter 18).
4
The PDF printed for each employee.
When
For each per-employee form the law requires. Monthly returns and electronic files are their own models with an export (Chapter 17).

Two habits from the larger modules apply to every filing. Map payslips to boxes with data: Mexico stores the official concept code on each rule, so a new allowance needs a rule, not a change to the export. And collect every validation error before raising, so the payroll officer fixes ten missing tax numbers at once rather than one per try.

The accounting bridge says which account each rule posts to. The core finds a method named after the chart, _configure_payroll_account_<chart code>, and calls it whenever a company loads that chart. Following the Mexican one:

def _configure_payroll_account_xx(self, companies):
    wages = 'xx_account_wages'                    # ① xml ids in the l10n_xx chart
    wages_payable = 'xx_account_wages_payable'
    rules_mapping = defaultdict(dict)
    basic = self.env.ref('l10n_xx_hr_payroll.l10n_xx_regular_pay_basic')
    rules_mapping[basic]['debit'] = wages         # ②
    net = self.env.ref('l10n_xx_hr_payroll.l10n_xx_regular_pay_net')
    rules_mapping[net]['credit'] = wages_payable
    self._configure_payroll_account(              # ③
        companies, "XX", account_refs=[wages, wages_payable],
        rules_mapping=rules_mapping, default_account=wages_payable)
1
Accounts by xml id of the country's chart, so the mapping works in every company whatever the account numbers.
2
One debit or credit per rule: the cost side of earnings, the liability side of deductions and of the net (Chapter 16).
3
The core helper sets the payroll journal on the country's structures and writes the accounts on each rule, company by company. An account it cannot find only logs a warning: the rule stays without an account and the entry gets an Adjustment Entry line.

The account module also ships two small data files, both noupdate because accounts are the company's choice and the weekly reload must not overwrite them:

Common pitfall: rules activated after the chart

A mapping that finds its rules with a search skips archived ones. Belgium installs many rules archived and activates them when the employer's sector is chosen; if the chart was loaded first, those rules have no accounts and the first entry shows a large Adjustment Entry. The fix is to run _load_payroll_accounts again for the company once the rules are active, not to type accounts rule by rule.

22.9 Tests

Chapter 21 explains golden payslips and which situations to cover. This is the test file that holds them, in the account module, following the Dutch one:

@tagged('post_install_l10n', 'post_install', '-at_install', 'payslips_validation')  # ①
class TestPayslipValidation(TestPayslipValidationCommon):

    @classmethod
    @TestPayslipValidationCommon.setup_country('xx')                       # ②
    def setUpClass(cls):
        super().setUpClass()
        cls._setup_common(                                                 # ③
            country=cls.env.ref('base.xx'),
            structure=cls.env.ref('l10n_xx_hr_payroll.hr_payroll_structure_xx_employee_salary'),
            structure_type=cls.env.ref('l10n_xx_hr_payroll.structure_type_employee_xx'),
            version_fields={'wage': 5000},
        )

    def test_regular_payslip(self):
        payslip = self._generate_payslip(date(2025, 1, 1), date(2025, 1, 31))
        self._validate_worked_days(payslip, {'WORK100': (23.0, 184.0, 5000.0)})   # ④
        self._validate_payslip(payslip, {                                  # ⑤
            'BASIC': 5000.0, 'GROSS': 5000.0,
            'XX_OLD_AGE': -524.01,    # capped: 35,129 / 12 × 17.9 %
            # ... every other line, from the independent calculation
        })
1
Tags. The test runs after every localization is installed, as in a real database with several countries, and can be run alone with the payslips_validation tag.
2
A company of the country with its chart of accounts. That is why the test lives in the account module.
3
One employee, one version, one structure. version_fields is the situation under test; other tests change it (self.version.l10n_xx_30_percent = True).
4
Time first: days, hours and amount per time type. If these are wrong, no rule can be right.
5
Every line, with its source. A line the dict does not list also fails the test, so a rule that suddenly applies is caught.

When a test fails, _validate_payslip prints a table with one message per code. Each points to a different place:

WRONG CALCULATION: the line exists, its total differs. Check the parameter value for the period, the rounding, the sequence.
MISSING LINE: a line the test does not expect appeared. A condition became true.
RULE NOT COMPUTED: an expected line is absent. Check the condition, the structures, an input code, an activation switch.

For payslips with dozens of lines, _validate_payslip(payslip) without a dict compares with a JSON snapshot in tests/test_files/payslips/. Review the snapshot's diff in the pull request as carefully as code: it is the expected result.

In practice: build in this order

Each step is a pull request that runs and can be reviewed alone. 1 · The country's time types in community. 2 · A skeleton that installs with no warning. 3 · Categories and parameters. 4 · Rules, with golden tests for a low and a high income. 5 · Version fields and helpers. 6 · Declarations. 7 · The accounting bridge: a pay run posts a balanced entry with no Adjustment Entry line.

22.10 The yearly upkeep

Every year the law publishes new values, usually in December for 1 January: a new tax scale, a higher cap, a new minimum wage. The design of Part IV turns that into a data job. Suppose country xx raises the old-age cap of §22.5 from 35,129 to 36,000 (placeholder values) on 1 January 2026:

sequenceDiagram
    autonumber
    participant DEV as Developer
    participant XML as Parameter file
    participant CRON as Weekly job
    participant DB as Customer DB
    participant SLIP as Payslip
    DEV->>XML: new value from 1 Jan 2026
    DEV->>DEV: tests on both sides
    XML-->>CRON: shipped with code update
    CRON->>DB: reload listed files
    DB-->>SLIP: value valid at end date
    Note over DB: edited by customer? skipped until Reset

Step by step:

1
Add, never edit. The developer adds a value next to the 2025 one. Editing the 2025 record instead would rewrite every 2025 payslip recomputed later, and break the 2025 tests.
2
Test both sides of the date (snippet below): December still reads the old cap, January the new one.
3
Merged and shipped in the supported versions. No module upgrade is needed on the customer side.
4
The weekly job Payroll: Update data reloads the listed files into every database: the new record is created, untouched records are refreshed.
5
The next payslip ending on or after 1 January reads 36,000; a December payslip recomputed later still reads 35,129.
!
Customer edits are protected (the note in the diagram). If the customer edited this parameter, the job skips it and the new value never arrives, until someone clicks Reset (Chapter 21). When a customer reports that "the new rate did not come", look there first.

Steps 1 and 2 are the developer's whole job:

    'OLD_AGE': [17.9, 36000.00],

}</field>

def test_old_age_cap_both_sides(self):
    december = self._generate_payslip(date(2025, 12, 1), date(2025, 12, 31))
    self._validate_payslip(december, {'XX_OLD_AGE': -524.01}, skip_lines=True)  # 35,129 / 12 × 17.9 %
    january = self._generate_payslip(date(2026, 1, 1), date(2026, 1, 31))
    self._validate_payslip(january, {'XX_OLD_AGE': -537.00}, skip_lines=True)   # 36,000 / 12 × 17.9 %

Same shape, new id, new date: the rule does not change. The test uses a wage above both caps, otherwise the cap is never reached and the test passes even if the new value is wrong; skip_lines=True checks only the line the change affects. Belgium's professional-expenses cap is the same pattern in a real module: a …_2025 record at 5,930 and a …_2026 record at 6,070, side by side.

Not every change is a new value. Three kinds come back every year:

A new value
a rate, a cap, a tax scale, a minimum wage
You doadd a dated record with a new id; same shape
Arriveswith the weekly job
Testone payslip before the date, one after
A rule fix
the method was wrong, or the law changed the method
You doedit the rule's XML; if old periods keep the old method, switch on a parameter, since rules are not dated
Arriveswith the weekly job
Testthe golden payslip that showed the bug; old tests unchanged
A new filing format
the administration changes a file or a form
You dochange the export code, keyed on the period it applies to
Arriveswith the code update; no data
Testan exact-file or snapshot test

The upkeep also includes the check of Chapter 11: once a year, compare each value with its official source, line by line.

22.11 How to review a localization

Review in a fixed order, the order of the cards below: law first, because a perfectly coded wrong rate is still wrong; screens and filings last, but never skipped. Grade each finding:

blocker wrong pay, a wrong filing, or a module that cannot be used. Request changes.
major wrong in a realistic case, or a maintenance trap. Fix now, or a ticket with an owner.
minor clarity, screens, style. A comment.
1Law
  • blocker
    Every rate, cap and threshold cites an official source.
  • blocker
    Each date_from is the date the law takes effect.
  • major
    A new value keeps last year's shape.
2Data
  • blocker
    Module named l10n_<cc>_…; every rule, structure and parameter file in _get_data_files_to_update, in load order.
  • major
    Every legal number is a dated l10n_<cc>_ parameter, and every parameter is read by a rule.
  • major
    New values are added; no past value is edited.
  • major
    Each piece of data the rules or filings need has a payroll warning; blocking only where every payslip would be wrong.
3Rule code
  • blocker
    Every category, code, input and field a rule reads exists and is filled earlier.
  • blocker
    Each rule is on every structure where the law applies it.
  • major
    No legal number as a literal (25 *, 0.4); rounding only where the law rounds.
  • major
    Categories and structures written as (6, 0, […]).
  • minor
    Sequences leave gaps; long formulas sit in helpers.
4Engine and overrides
  • blocker
    Every override has a country guard and calls super().
  • major
    No search per payslip; batch data in _get_common_localdict.
  • major
    A version field a rule reads is in _get_fields_that_recompute_payslip.
5Tests
  • blocker
    Expected values come from an independent calculation, with the source in a comment.
  • major
    Both sides of each dated change; one income above every cap and in the top bracket.
  • major
    Every structure and every frequency has a payslip test.
6Security
  • blocker
    Salary fields carry groups="hr_payroll.group_hr_payroll_user".
  • blocker
    Every new model has access rights and a multi-company rule.
  • major
    No rule writes on a record.
7Screens
  • major
    Country fields show only for the country (invisible="country_code != 'XX'").
  • minor
    Labels and help in plain English; the payslip PDF readable by an employee.
8Filings and accounting
  • blocker
    A test pay run posts a balanced entry with no Adjustment Entry line.
  • blocker
    Declarations read payslip lines, through codes or a data mapping; they never recompute.
  • major
    Filing checks collect every error before raising.

Common bugs we found

Reading Odoo's own payroll modules for this book turned up the same four patterns again and again. Look for them first.

A total nobody feeds
A rule reads a category that no rule adds to. It reads 0, with no error.
Seen ascommissions never enter a pension base
Card3 · Rule code
A literal next to its parameter
The number is typed in the rule while a parameter for it exists and is never read.
Seen asMexico's contribution cap: 25 * in the rule, and a parameter worth 25 that no rule reads
Card2 · Data, 3 · Rule code
A bracket right only for low incomes
The formula is wrong above the second band, and every test is below it.
Seen asmin(gross - low, high) instead of min(gross, high) - low
Card5 · Tests
A lookup that silently finds nothing
A missing record only logs a warning, and the code goes on without it.
Seen asaccount ids absent from the chart: rules without accounts
Card8 · Filings and accounting

Common pitfall: the green test run

Tests run as an administrator, so a missing access right never shows; and most of them create one company. Before approving, open a payslip in a database with several localizations installed, logged in as a payroll user of the new country's company only.

Worked example: reviewing a one-line change to a contribution cap

A pull request changes Mexico's SBC rule from 25 * payslip._rule_parameter('l10n_mx_uma')['daily'] to read the multiplier from l10n_mx_imss_limit_with_uma. Card 1: is the source of the 25 cited? Card 2: a parameter nobody read becomes used, good. Card 5: is there a payslip with a daily salary above 25 times the reference unit? If not, ask for one: a suite of ordinary wages would stay green even if the cap were deleted.

Summary

  • A payroll localization is the country layer: l10n_xx_hr_payroll for the law, l10n_xx_hr_payroll_account for the accounts and the tests, built on the shared hr_payroll. The l10n_<cc> prefix makes Reset work.
  • Most of it is data: a structure type and structures, categories designed from the declarations, rules that write every field and contain no legal number, and dated parameters with a stable shape. Payroll warnings catch missing data on the dashboard, and block validation only when every payslip would be wrong.
  • Three hooks wire it in: the list of files the weekly job reloads, the post-install switch to the country's time types, and the allowed pay frequencies.
  • Python is for facts about the person (fields on the version, mirrored on the employee) and for engine steps the law changes, always behind a country guard and with super().
  • The module must produce the payslip PDF, the declarations (read from payslip lines) and the journal entry, through a rule-to-account mapping.
  • Golden-payslip tests prove it. The yearly upkeep is a new dated record with a test on each side of the date; the weekly job delivers it, except to records the customer edited.
  • Review along eight cards (law, data, rule code, engine, tests, security, screens, filings), grade each finding blocker, major or minor, and look first for the four known bug patterns.
